#### D1.2.2 ITEM WMS Dynamic Form｜40 分钟

##### D1.2.2.1 业务结果、改造前流程与演示边界（建议）

**已知事实。**仓库经常需要异常登记、状态采集、任务确认和临时分析页面。传统方式要反复解释需求、等待开发、联调和上线；生成一个看起来正确、却不了解 WMS 字段与接口的页面，也不能直接解决问题。案例的验证点是：代码生成与运行要落在 WMS 本地环境；这里的“本地”指基于既有 WMS 代码、业务模型和约定的开发/验证环境，不是脱离现有软件重新搭一个通用页面。

**建议把业务结果定义为可验证的结果链，而不是速度口号：**

1. 业务人员能够完整描述一个仓库异常登记需求，并明确必填信息、角色和状态变化。
2. 生成的动态表单在既有 WMS 代码和本地样例数据上运行，字段、组件、权限和接口命名与现有约定一致。
3. 异常登记可经过校验、人工确认和必要 Action，形成可追溯的状态回写；“生成成功”不等于“生产上线成功”。
4. 留下代码审核、功能测试、接口测试、发布/回滚责任与失败样本，支持后续维护和 ISS 迁移判断。

**建议演示场景。**使用仓库异常处理：记录订单、料件、位置、异常类型、照片和处理建议；确认后更新状态。演示中应分别标出真实环境、脱敏数据和模拟数据，不把模拟状态回写描述成真实生产结果。

**建议展示改造前交接：**仓库人员发现异常 → 口头或消息说明需求 → 业务/IT 反复澄清字段和规则 → 开发修改页面或接口 → 联调与等待 → 上线后再反馈缺陷。每个箭头旁记录责任人、输入、等待点和可能丢失的信息。

**待补证据：**实际使用的 WMS 版本、源码可用范围、可授权的本地环境位置、真实或脱敏异常样本、字段/接口/状态字典、现行开发交接时长、改造前缺陷或返工记录、演示录像及数据处理批准人。

##### D1.2.2.2 改造后闭环：从任务到受控状态回写（建议）

建议把闭环拆成六个可观察状态：

1. **正常任务。**用户提出“登记仓库异常”需求；系统展示订单、料件、位置、异常类型、照片和处理建议字段。已知路径是自然语言提出需求并生成与既有 WMS 约定一致的页面；字段映射和接口名称仍需现场确认。
2. **缺失信息/异常。**缺少订单、位置或异常类型时，表单阻止提交并提示补齐；照片格式、接口超时、无效状态或重复提交应进入明确错误分支。具体必填规则、错误码和重试策略为待补证据。
3. **人确认/接管。**状态更新、跨库存影响、异常关闭或其他高风险 Action 先由授权角色确认；证据不足、权限不足或模型/生成结果不确定时，转业务人员或 IT/DT 支持，不由 iCEO 或生成结果替代正式业务决策。
4. **状态回写。**只有通过字段校验、权限判断、业务审核和接口测试的路径才允许回写；保留原状态、新状态、操作者、时间、原因和关联附件。是否存在真实可用的状态接口、审计字段和回滚 API 需补证。
5. **最终业务结果。**建议以“异常记录可追溯、状态与 WMS 一致、责任人可查、失败可回退”作为验收条件，不预设已达成的效率、质量或上线结果。
6. **证据留存。**保存生成前需求、生成版本、人工修改、测试样本、接口响应、审核结论和发布/回滚记录，支持维护与迁移。

##### D1.2.2.3 实施过程、困难与业务采用（建议）

**输入与建设过程。**在授权范围内理解既有代码结构、字段、组件、权限、校验逻辑及接口；建立可复现业务流程的本地验证环境和样例数据；由用户用自然语言提出页面需求；生成后补齐字段校验、角色权限、错误处理、状态更新与必要 Action；再进行代码审核、构建、功能与接口测试，按发布流程进入目标环境。

**可能困难（不要写成历史事实）：**源码或接口不可得；本地环境不能复现关键状态；字段语义只存在于专家经验；生成页外观正确但绑定了错误字段；权限和错误分支遗漏；状态回写会影响库存或订单；环境升级后组件契约变化；演示数据不能用于真实回写。

**建议克服机制：**先做访问与环境清单；用最小脱敏样例建立可复现测试；用字段/状态/接口映射表由业务专家确认；把权限矩阵、错误目录、Action 白名单和回滚路径作为生成后的必检项；每次修改保留版本和差异；把失败样本加入回归集；不满足条件时缩小范围、模拟 Action 或转交 DT，而不是强行发布。

**建议推动采用。**先让一名授权业务用户完成一条低风险异常登记，再由专家复核字段、状态和错误处理；通过短反馈循环更新模板、组件、字段、Action 和测试用例；明确使用说明、升级窗口、问题入口、运营责任和停止/回滚条件。未取得真实采用数据前，不宣称用户普及、组织转型或维护成本下降。

**待补证据：**实际参与角色与姓名、需求澄清轮次、生成/人工修改记录、阻塞问题及解决时间、环境升级影响、用户试用反馈、培训材料、采用率、停止/回滚执行记录。

##### D1.2.2.4 组织与价值证据：验收和运营口径（建议）

**职责边界。**ITEM 直接对接 COO AI Team/Hollis，紧密共同开发并依托现有成果；ISS Biz（team）负责业务 Owner、场景规则、专家确认、业务验收与采用/价值判断；DT 按需支撑数据、代码、软件、接口和跨部门依赖。人员可以兼任，但每个场景仍应登记业务 Owner、FDE、专家审核人、系统/数据责任人、审批人、运营维护人和回滚授权人。

**建议验收包：**

- 需求与字段映射：订单、料件、位置、异常类型、照片、处理建议的来源、类型、必填与敏感级别。
- 交互与权限：角色可见范围、可编辑字段、提交/确认/接管条件、错误和拒绝路径。
- 技术与接口：构建记录、功能测试、接口测试、状态回写、审计日志、版本和回滚路径。
- 业务与运营：专家签字、业务 Owner 验收、问题分级、反馈入口、升级责任和维护窗口。

**建议指标口径，不预设结果：**以改造前基线和同口径周期比较需求澄清轮次、开发/联调/等待时长、人工修改量、字段/接口测试通过率、缺陷数量与严重级别、回滚次数、维护工时、采用率和异常闭环时间。必须写清分母、样本来源、观察周期、是否剔除模拟数据及数据责任人。

**待补实测结果：**当前没有可引用的实际开发周期、沟通次数、人工修改量、测试通过率、上线后缺陷、缺陷严重级别、维护成本、采用率、回滚次数或业务收益；这些不能被写成已实现 KPI。

##### D1.2.2.6 思考：业务变更链与可沉淀资产（建议）

**业务变更链：**业务提出规则或页面变更 → 专家审核字段、状态和例外 → FDE 在 WMS 代码与本地环境中修改 → 功能/接口回归 → 业务 Owner 验收 → 按发布流程发布或回滚。每个环节都应保存版本、责任、证据和未决项；不能把自然语言需求直接等同于生产变更。

**可沉淀到核心知识库的授权/审核知识：**WMS 对象和字段定义、状态机、角色权限、组件/接口约定、Action 白名单、错误与接管规则、脱敏要求、测试用例、评测分母、发布与回滚 SOP、失败样本和维护责任。

**可沉淀的流程/Skill/评测/运营机制：**需求结构化模板、代码理解清单、动态表单生成 Skill、字段/权限/接口检查 Skill、异常分支回归集、构建与接口测试门、版本目录、缺陷分级、反馈与停止机制。知识只有在授权、审核、版本和责任齐全时才可复用。

**第二场景复用与重验证。**可复用：需求模板、审查清单、版本和回滚框架、通用测试结构。必须重验证：对象/字段语义、状态机、接口、角色权限、数据敏感性、业务专家和 Action 风险。不能因为第一个页面通过就推断所有 WMS 场景或模型能力都通过。

##### D1.2.2.7 可重复交付与现场动手（建议）

**方法流程：**授权与范围确认 → 代码/字段/权限/接口盘点 → 建立本地可复现环境 → 用自然语言生成小范围页面 → 补校验、错误、权限和 Action → 业务/专家审核 → 构建与功能/接口测试 → 受控发布、观测、维护或回滚。

**通用核心与配置边界：**核心是需求结构化、证据留存、审核门、测试门、版本与回滚；按场景配置的是字段、状态、角色、异常类型、Action 白名单和接口映射；环境、数据和跨部门系统是部署依赖；评测与维护不能省略。

**建议现场动手。**让授权业务用户修改一个低风险规则，例如把“异常类型”新增一个待审核选项，或调整“处理建议”字段为必填；现场产出一页小范围草稿、字段/状态/权限卡、验收条件和责任表。若不能接触真实代码或接口，则用脱敏/模拟数据展示草稿，并明确未完成真实回写。

**失败例的缩小/停止/转交机制：**源码不可得时停止声称本地验证，转为需求和接口盘点；状态回写无审计或无回滚时只做只读/模拟 Action；权限边界不清时转交 ISS Biz 与 DT/安全审核；回归失败时回到上一版本并保留失败样本。任何失败都不强行产品化。

**现场交付物建议：**一张能力卡、一份字段/权限/接口映射、一组最小验收用例、一个责任矩阵、一个失败与回滚记录。待补的是实际修改内容、参与人、测试结果、是否进入目标环境及后续维护 Owner。

##### D1.2.2.8 既有详细实践与边界补充

##### 验证点：代码生成与运行落在 WMS 本地环境

此处“本地”重点是基于既有 WMS 代码、业务模型和约定的本地开发/验证环境生成并验证功能，不是脱离现有软件重新搭一个通用页面。具体设备、部署位置和代码权限需按实际演示环境说明。

##### 痛点

仓库经常需要异常登记、状态采集、任务确认和临时分析页面。传统方式要反复解释需求、等待开发、联调和上线；生成一个看起来正确、却不了解 WMS 字段与接口的页面，也不能直接解决问题。

##### 解决路径

**WMS 代码 → WMS 本地环境 → 自定义页面 → 校验、测试与受控发布。**

1. 在授权范围内理解既有代码结构、字段、组件、权限、校验逻辑及接口。
2. 建立能够复现业务流程的本地验证环境和样例数据。
3. 用户用自然语言提出页面需求，生成与现有 WMS 约定一致的页面、字段和交互。
4. 补齐字段校验、角色权限、错误处理、状态更新与必要 Action。
5. 进行代码审核、构建、功能与接口测试；通过发布流程进入目标环境。

演示需求可使用仓库异常处理：记录订单、料件、位置、异常类型、照片和处理建议，确认后更新状态。不能把“代码生成成功”直接当作“生产上线成功”。

##### 演示与证据

建议完整展示一次需求描述、代码生成、本地运行、业务修改、测试和状态回写。观察生成页面是否使用了正确字段、权限和接口，是否能够跟随现有软件升级。

评估开发周期、业务反复沟通次数、人工修改量、测试通过情况、上线后缺陷以及维护成本，而不只记录生成代码的速度。

##### 持续优化与 ISS 迁移

沉淀标准模板、组件、字段、Action 和测试用例，避免无限制个人定制形成新的维护负担。代码资产和业务应用分别保留版本、责任与回滚路径。

迁移到 ISS 时，首先确认现有软件和源码可用范围；需要代码、接口或跨部门系统支持时按需引入 DT。业务人员无需自己写代码，但正式发布仍需满足企业工程与安全要求。

**本节结论：**哪个 ISS 页面适合快速验证？能否取得必要代码和本地环境？生成、审核、发布及后续维护分别由谁负责？
