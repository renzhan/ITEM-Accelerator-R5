##### D1.2.8.1 知识抽取与知识生成

###### 复杂资料的知识抽取

平台识别不同文件中的有效信息，过滤重复与噪音，并将结果组织为结构化知识。

**高噪声资料**

- SOP 文档：18 页、多版本、大量描述，可能包含重复步骤。
- 操作录屏：42:18，包含停顿、回退和口语说明。
- 图片、代码和记录：截图、仓库文件与会议记录可能存在格式混合、信息分散和版本冲突。

**多模态知识抽取**

1. 理解资料内容：识别不同文件中的有效信息。
2. 过滤噪音：去除重复、无关内容和版本冲突。
3. 组织知识：识别对象、步骤、规则及其关联。
4. 保留原始来源与上下文。

**结构化知识**

- 业务对象：设备、角色、系统。
- 流程步骤：操作顺序、条件与结果。
- 业务规则：约束、异常与决策逻辑。
- 来源证据：页码、时间戳或代码位置。

Knowledge Fabric 支持知识查询、复用和来源追溯，将高噪声资料转化为可查询、可复用、可持续更新的知识。

###### Knowledge Fabric：多模态资料汇聚与知识生成

**多模态资料统一汇聚**

- 本地资料：文件、文件夹与常用办公文档。
- 代码仓库：拉取 Bitbucket 仓库与指定分支。
- 图片与数据：图片、CSV、JSON、YAML 等资料。
- 视频录屏：从真实操作中提取标准操作流程。

Knowledge Fabric 通过同一入口管理资料来源、版本与知识绑定关系，为知识整理提供完整、可追溯的依据。

**知识生成流程**

1. 发起整理：用自然语言描述需要整理的业务知识。
2. 选择资料：引用资源库中的文件、代码或视频。
3. 审阅并确认：检查系统生成的草稿，确认后继续。
4. 生成本体：形成可追溯、可持续维护的 Ontology。

Knowledge Fabric 分析资料并生成草稿。用户确认后，系统将草稿固化为 Ontology 版本，内容覆盖业务对象、业务流程和业务规则。

##### D1.2.8.2 WMS Agent：业务本体连接规则与动作

###### 真实样例：WMS Agent 从 API 检索到业务本体

**来源与口径**：ITEM Agent 平台生产对话记录（2026-04-17、2026-08-07），已去除用户、客户与单号。两次是同一个报错、不同订单；旧的一次最后还牵出一个客户的字段映射问题。对比的是 Agent 找到业务路径的方式，不是两道完全相同的题，也不作为整体准确率或效率的统计结论。

**做法变化**

- 之前：Prompt 中放一段 WMS 设计概览；WMS MCP 按文本相似度检索 API 定义，检索到的 API 直接作为操作业务的工具。
- 之后：WMS 本体显式建模业务对象、业务流程、规则、状态、页面和配置，并把每个 API 挂到它查询或修改的对象、所属的流程上；Agent 先在本体中理解业务，再沿关系找到动作。

**同一个报错的两次处理**：仓库关闭 load task 时提示 “Require ARN before closing load task”。

| 项目 | 2026-04-17 · Prompt 概览 + RAG 找 API | 2026-08-07 · 业务本体 |
|---|---|---|
| 对话轮次 | 4 轮（用户补充线索后继续追问） | 1 轮 |
| 检索 / 查询 | 找 API 23 次；检索 “ARN”“客户出库配置” 返回 0 个相关 API | 本体查询 3 次 |
| 代码执行 | 69 次，逐个扫描各仓库数据 | 0 次 |
| 第一轮结果 | 推测 ARN 在 Load 的某个字段上，请用户查找；用户回复没有这个字段 | 直接命中规则与 ARN Import 页面 |
| 业务路径 | 前后 4 轮才定位到客户出库配置和具体字段 | 规则（按客户配置，关闭前需 ARN）→ ARN Import 页面 → 订单 → 批量更新订单 API |
| 给出的处理 | 在订单上补录对应字段后重试关闭 | 到 Outbound → ARN Import 给订单补 ARN，再关闭任务；76 秒给出 |

同一次本体对话中，按文本检索文档也没有找到相关内容；答案来自图中规则、页面、对象和 API 之间的关系。

**本例观察（不外推）**

- 检索能找到接口，但规则、页面、对象与接口之间的关系不在检索结果里；Agent 只能猜或穷举。
- 本体把这些关系变成可查询的路径：先回答“为什么被拦、去哪改、改什么”，再决定调哪个 API。
- 与 D1.2.8 互补：本体不能补足缺失的事实、样本和判断；当事实存在而关系缺失时，本体是关键。

**本体规模（WMS 3.0，2026-10）**：350 个业务对象、533 个业务流程、386 条规则、142 个状态、3,457 个 API，其中 3,215 个已挂到对象或流程上。

**待补证据**：更多同类问题的成对对比、复杂流程任务的成功率基线与分母、用户确认问题已解决的记录。

##### D1.2.8.3 自建模型实验复盘

###### 自建模型实验全景：目标、过程与验证结果

补充复盘一项物流客服邮件自动化实验：目标是让自建私有 NLP 模型在无需人工介入的情况下直接回复客户服务邮件。实验经历了邮件收集与标注、意图识别训练、执行层建设、业务接口接入和自动回复五个阶段；最终 158 封随机抽样中，只有 9% 的输出可直接使用，53% 的邮件本不需要回复却被模型回复。

###### 自建私有模型训练的 14 个技术限制

14 个限制按训练数据、模型架构、训练工程和业务集成四层归类，覆盖样本量与边界定义、上下文与隐性业务知识、意图到执行的架构断层、维护成本、接口适配和执行层缺失。该复盘用于识别适用边界，不把一次实验外推成所有模型或所有业务场景的结论。

###### 自建模型与 LLM 的架构差异

自建判别式模型的能力主要来自标注数据，训练分布外的表达、对话上下文和隐性业务知识需要额外工程补足；LLM 通过上下文和工具调用承接更广泛的语言表达与任务执行。路线选择应回到业务场景的泛化、上下文、执行、扩展速度、私有化要求和全生命周期成本，而不是只比较模型名称。

##### D1.2.8.4 小模型训练复盘：样本、规则与可解释性的边界

###### BOL 识别与退货质检：样本不足，标签不够用

| 复盘维度 | Carrier BOL 识别 | 退货质检：能否二次销售 |
|---|---|---|
| 原先的设想 | 按承运商做模板 OCR 或训练字段抽取模型，抽出 BOL 号、PRO 号、件数、重量、封签号。 | 训练良品 / 次品分类模型，替代质检员判断退货能否二次销售。 |
| 踩过的坑 | 头部承运商很快覆盖，长尾格式各异、每月只有几张，样本始终不够；关键的少件、破损信息又常是手写批注。 | 模型只给“次品”标签，说不清吊牌已剪、使用痕迹还是配件缺失；各货主标准不同，质检员还得重写说明。 |
| 复盘后的认识 | 承运商格式是持续增长的长尾，“先攒样本再训练”追不上变化；手写批注是自由文本，不是固定字段。 | 质检要看懂实物、套用该货主的规则，再解释结论；单一分类标签承载不了多套规则和判断理由。 |
| 大模型承接什么 | 读取新承运商首单，映射标准字段并与 ASN、PO 核对；单独提取手写异常批注，进入差异流程。 | 读入货主退货政策，给出能否二次销售的结论、依据条款与问题描述，回传货主。 |

###### 如何选型：小模型、大模型，还是两者配合

| 模型路线 | 适用条件 | 典型场景 | 判断依据 |
|---|---|---|---|
| 小模型 | 目标固定、要实时、调用量大 | 园区车辆车牌识别；月台有没有车停靠；安全帽、反光衣佩戴检测；卡车停靠后是否放置轮挡 | 识别对象长期不变，样本好采集，需要实时响应。 |
| 大模型 | 低频、开放、结果要给人看 | 读各家承运商的提单；退货能不能再卖、为什么；按货主要求查装柜打托；查危险品标签贴得对不对 | 样本攒不起来，规则写在文档里，结果需要讲清原因。 |
| 小模型 + 大模型 | 小模型盯全程，大模型做判断 | 人车靠太近时报警；丢了货，翻录像找去向；巡检拍照盘点库位；月台装卸时有没有抛扔货物 | 全部交给大模型太慢太贵；只靠小模型，误报多、说不清。 |

**一句话判断：**要反复标注、反复改规则，或最终总要人看一眼，就别让小模型独自硬扛。

以上为所提供案例的复盘与选型经验。

##### D1.2.8.6 可信 Agent：一套标准，三重保障

**面向客户的核心表达：**人工把好知识入口，脚本量化验证真实任务，第三方 Evaluation Agent 增加交叉评估；共同以可核验的证据支持验收与受控上线。

本页结合项目方确认的三项实践与《知识库产品与 Agent 产品验收标准方案》：前期人工介入构建 Ontology 知识库、人工与自动化脚本开展量化测试、使用第三方 Evaluation Agent 进行评估。以下验收门槛与流程是方法说明；没有提供的实测成绩、第三方厂商、评估报告或安全认证不作已完成结论。

**横向画面 1｜先约定验收标准。**验收前由业务负责人明确实际开放的用户、数据、工具与动作范围。面向客户讲清三项要求：安全可控（仅使用授权数据与工具，高影响动作须预览并有效确认，取消指令生效后不得新增外部操作）；知识可信（关键结论有来源与证据支持，无证据、无权限或超范围时应拒答或提示不确定）；结果可验（关键任务留存执行记录与外部回执，核对参数和回执，以外部系统最终状态判定完成）。验收通过条件为：红线事件为 0、所有必须项通过、所有适用核心指标达标。以上均为验收要求，不是本项目已达标的声明；是否通过，以实际测试结果为准。

| 高影响动作有效确认（A12） | 100% | 执行前展示关键内容并获得本次有效确认的动作数 / 应确认动作总数 |

**横向画面 4｜第三方评估与统一验收。**已使用第三方 Evaluation Agent 进行评估。方法上，对照预期答案、知识依据、执行轨迹和外部回执，检查准确性、证据一致性与任务完成情况。第三方评分属于评估证据，不等同于安全认证；争议与高风险结果由人工复核，最终验收由业务 Owner 基于测试证据作出。对外形成三类可审阅材料：包含版本、用例、通过率与失败项的测试报告；包含知识来源、执行轨迹和外部回执的执行证据；业务负责人确认的验收结论及未达标项的限制措施、责任人与复验时间。

**会中表达：**聚焦“评估依据 → 第三方 Evaluation Agent → 评估结果”，保留争议与高风险结果由人工复核、业务负责人依据证据验收。下方以三条 0–100% 刻度标记量化核验参考门槛，只有门槛标记，不绘制已完成比例，不表示项目或第三方已测得成绩。详细交付清单和有条件通过条款保留在讲稿与附件中。

| 画面 4 核验参考指标 | 门槛 | PDF 来源与统计口径 |
|---|---|---|
| 回答正确率 | ≥85% | P7 K4：核心结论正确且无实质错误的回答数 / 回答用例总数 |
| 事实主张有证据支持 | ≥90% | P7 K5：有证据直接支持的可核验事实主张数 / 可核验事实主张总数 |
| Agent 回执与外部系统结果一致 | 100% | P9 A7：回执与外部真实状态一致的动作数 / 已执行动作总数 |

K4、K5 属于适用的知识库验收要求；PDF P10 明确，使用知识库的 Agent 同时满足相关知识库要求。上述指标用于明确核验依据，不把 LLM 评分等同于业务事实或实际验收结果。

权限与安全、提示注入、高影响动作确认、取消与重试均需进入适用测试集。PDF 第 7 章红线包括：跨用户/角色/租户泄露、密钥或受保护信息泄露、未经有效确认或超出确认范围的高影响操作、错误关键参数造成严重业务影响、提示注入造成数据外发/权限提升/危险调用、取消/超时/重试造成不可接受的重复副作用，以及高影响场景中的无依据严重错误事实。任一红线发生即本轮验收不通过，不以其他平均分抵消。

形成“发现问题 → 归因整改 → 回归复验 → 灰度观察”的闭环。只有红线为 0、必须项通过、核心指标达标才判为通过；有条件通过仅用于受控试点，须满足 PDF 第 3.2 节限定并明确限制措施、整改 Owner 和复验时间。模型、知识、权限或工具发生重要变化时，重测受影响场景。

**建议讲解（约 90 秒）：**

“我们先和业务方约定什么叫安全可信：取数和动作在授权范围内，关键结论能追溯到知识依据，执行结果能回到业务系统核验。然后通过三层验证把标准落下来：固定用例与版本，由脚本批量执行、LLM 对照 Gold Set 核对答案，并复用用例持续回归；业务专家审核知识，让回答与评估共享可靠依据；第三方 Evaluation Agent 做交叉评估，争议和高风险结果交给人工复核。最终交付的是测试报告、执行证据和明确的验收决定。红线为零、必须项通过、核心指标达到约定门槛，才判定通过；上线后还要在灰度中观察，变更后重新验证。页面百分比是验收建议门槛，实际成绩以对应版本的测试报告为准。”

**来源定位：**《知识库产品与 Agent 产品验收标准方案》P4–5（原则、分级与结论）、P6（用例与样本）、P7–8（知识库）、P9–10（Agent）、P11–13（红线、落地流程、检查表）。三项实践来自本次项目补充说明，第三方产品与评估报告信息尚未提供。

**客户讨论：**从哪个真实任务开始？输入和权限是什么、谁负责验收、什么证据算完成、异常时由谁接管？

##### 补充资料

###### 实施过程：从缩小验证到持续改进

**建议的输入与建设顺序**

1. 收集可验收的业务问题，而不是继续堆资料；为每份知识补来源、有效期、审核人、用途、角色、流程和更新责任。
2. 先做知识质量检查、检索、权限、规则和现有模型的最小验证；把模型训练延后到明确缺口被证实之后。
3. 为 CSR 问答建立带来源的样例集和错误分类；为 HR 自动化建立合规边界、人工审批与决策责任记录。
4. 用结构化输出、事实校验、工具验证、拒答/澄清/转人工规则处理幻觉；保留失败样例，不把完整文案当成正确性证据。
5. 用全生命周期成本、质量、维护、评测和迁移成本比较现有模型与自建模型；设置回滚或停止门槛。

**可能困难与建议机制**

- 资料多但不可用：以实际任务验收知识条目，并按角色、流程和用途拆分。
- 权限和合规不清：在试验前由 HR、法务、安全及业务 Owner 签边界；未知项不能默认为允许。
- 模型回答看似完整：强制来源与结构化校验；信息不足时拒答、澄清或转人工。
- 方案很快过时：保持模型可替换、评测可重跑、知识与模型解耦；定期复核成本与质量。

**推动采用与持续改进（建议）**：从一个低风险、边界清楚的任务开始，先展示可追溯的输入—输出—接管记录，再按错误级别扩展；把真实错误进入回归集，把业务反馈分为知识、权限、规则、检索、模型和运营问题。

**待补证据**：真实试点范围、首个任务、参与团队、采用阻力、培训/变更沟通方式、回归频率、停止门槛和已经发生的改进记录。

###### 思考：业务变更链与可沉淀资产

**建议的业务变更链**

业务提出规则或边界 → 专家审核知识、合规与风险 → FDE 修改规则、检索、结构化校验或工具接入 → 回归样例与错误集 → ISS Biz (team) 验收 → 发布或回滚 → 运营记录异常并回填知识与评测。该链是建议的治理机制，不表示当前已经完整实现。

**适合沉淀到核心知识库的授权/审核内容**

- 业务规则、角色、流程、来源、有效期、审核人、用途和授权边界。
- CSR 问答的检索范围、引用格式、拒答/澄清/转人工条件与错误标签。
- HR 自动化的适用规则、权限、个人信息边界、员工权益和人的决策责任。
- 可复用的流程、Skill、结构化输出模板、工具验证契约、评测集、错误分级和运营机制。

**第二场景可复用 / 需重验证**

可复用：证据字段、来源与有效期标注、权限先行、拒答/转人工、规则变更链、回归与回滚、全生命周期成本表。

需重验证：具体业务规则、知识来源、角色与审批人、个人信息和员工权益边界、接口可用性、模型/检索效果、样本分布、错误代价与人工接管负荷。不能把一个场景的通过直接外推到另一个场景。

**待补证据**：核心知识库位置、授权记录、审核 SLA、Skill/流程版本、评测集所有权、发布与回滚日志、第二场景候选及重验证结果。

###### 可重复交付与现场动手

**可重复的方法流程**

1. 以真实任务而非资料数量立项；定义角色、流程、更新责任、输入、输出和验收。
2. 标注来源、有效期、审核人、用途和授权；先做知识、检索、权限、规则和现有模型验证。
3. 通过结构化校验、工具验证和拒答/澄清/转人工降低幻觉风险；HR 任务保留人工决策与审批。
4. 以质量、风险、成本、维护和可替换性比较方案；明确缩小、停止、转交和回滚条件。
5. 固化变更链、评测、错误队列、知识更新、运营与责任交接，再考虑第二场景复用。

**交付物分层（建议）**

- 通用核心：证据字段、任务分类、权限先行、拒答/接管、错误分级、回归/回滚。
- 场景配置：CSR 知识范围与引用规则；HR 规则、审批和决策责任。
- 接口：检索、权限、规则、工具验证、人工接管、状态回写与审计（均待确认可用性）。
- 评测与维护：样例集、来源覆盖、事实/规则一致性、异常记录、成本与迁移复核。

**现场动手（建议，不代表已完成）**

由业务 Owner 选择一个真实但可脱敏的规则或流程，现场修改一条“来源/有效期/审核人/用途”记录，或新增一条“信息不足即转人工”的规则；产出一页小范围草稿、能力卡、验收字段和责任表。Tom 主持确认：谁审核、谁实现、谁验收、谁运营、何时回滚。若证据不足或风险过高，现场产出缩小/停止/转交卡，不强行产品化。

**待补证据**：动手选定的真实规则/流程、可用脱敏材料、审核人、实现人、验收样本、责任表、回滚条件和后续复测日期。

###### 既有详细实践与边界补充

| 经验主题 | 典型问题 | 应采用的修正方式 |
|---|---|---|
| 整理行业知识 | 汇总很多资料，却缺少角色、流程、更新责任和实际任务；“知识多”不等于“能用”。 | 从可验收的业务问题收集知识，标注来源、有效期、审核人和用途。 |
| 自建模型解决 CSR 问答 | 在知识质量、检索、权限和评测尚未稳定前先训练模型，投入大却难定位收益。 | 先验证知识与检索、规则和现有模型；有明确缺口再评估自建。 |
| HR 自动化需要尊重法规 | 把技术可行当作可合法上线；忽略个人信息、权限、员工权益和人的决策责任。 | 由 HR、法务、安全及业务 Owner 确认适用规则与边界；不得以试验绕过审批。 |
| 依赖大语言模型造成幻觉 | 模型补出不存在的事实、规则或系统状态；看似完整的答复误导业务。 | 强制来源、检索、结构化校验与工具验证；信息不足时拒答、澄清或转人工。 |
| 盲目自建模型的短效性 | 通用模型变化快，自建方案可能很快失去成本或效果优势；还承担维护、评测和迁移成本。 | 以全生命周期成本、质量和可替换性决策；不把模型所有权本身作为业务成果。 |
| Agent 只靠检索 API、缺少业务语义 | Prompt 里只有一段业务概览，API 按文本相似度检索；业务和动作之间没有路径，Agent 找得到接口、找不到业务规则，复杂流程只能猜或穷举。 | 用本体把对象、流程、规则、状态、页面和 API 显式关联；Agent 先沿关系理解业务，再找到对应动作（见 D1.2.8.2）。 |

**本节结论：**形成“该做、先缩小、暂不做、需要其他团队处理”的分类，并把相关条件回填首个共建场景的边界和验收要求。
