#### D1.2.5 General：Record & Reply｜20 分钟

> 本案例的新增设计均标注为【建议】；输入中没有提供实际运营结果、组织改造结果、排名或模型能力数据。相关未知项列入【待补证据】，不得在会中当作已实现事实。

##### D1.2.5.1 业务结果、改造前流程与交接【建议】

**业务目标。** 目标不是先要求业务人员写完 SOP，而是让 ISS Biz (team) 在授权范围内把“做得出来、说不清楚”的流程转成可审阅的结构化知识，降低知识采集门槛，尤其覆盖线下或尚未被系统完整记录的业务活动。候选场景包括 backlog 处理、物流数据采集、线下资料整理及跨系统操作；这些是待选择的适配方向，不代表本案例已确认采用了其中某一个。

**期望结果。** 建议把结果定义为：获得一份带来源、角色、输入、判断、系统切换、人工动作、例外、输出和不确定性标注的 SOP 草稿；由实际操作人员和业务 Owner 审核；再决定哪些步骤适合 Agent、Tool 或 Workflow。最终执行应在权限、沙盒和人工接管边界明确后进行。待补证据包括知识采集耗时、漏项率、专家修正量、失败率、后续维护成本及业务结果基线。

**改造前路径。** 业务人员通常需要先自行写完整 SOP、明确字段与例外，再交给专家或技术人员理解。真实操作还包含页面切换、口头判断、手工步骤和未记录经验，访谈或文字整理可能遗漏这些信息。建议在会中画出当前实际路径：业务人员示范或回忆 → 文字/访谈记录 → 专家澄清 → 技术判断能否自动化 → 开发或交接 → 业务验收。每个箭头应补上现有系统、责任人、等待时间和返工点；输入未提供这些实测值，不能预填。

**交接边界。** Tom 主持；ITEM 直接对接 COO AI Team/Hollis 紧密共同开发并依托现有成果扩展；ISS Biz (team) 作为业务 Owner 负责业务验收；DT 按需支撑数据、代码、软件、接口和跨部门事项。具体参与人、审批链、授权范围、系统清单和可用样本均为【待补证据】。

##### D1.2.5.2 改造后闭环：从演示到受控执行【建议】

1. **任务进入。** 实际操作人员在明确授权后录制操作，或导入可共享的示例视频；提交场景、目标、角色、系统、数据敏感性和期望输出。视频可是真实、脱敏或模拟，必须在记录中标明。
2. **知识提取。** 从视频提取操作顺序、输入、字段、判断条件、系统切换、人工动作、例外、结果和证据时间点，形成带置信度/不确定步骤的 SOP 草稿。若视频无法证明某个条件，保留“待确认”，不能用模型猜补。
3. **信息缺失/异常。** 缺少字段、画面不可读、角色权限不明、系统状态不一致、出现未授权数据或异常路径时，Agent 停止自动推进，生成问题清单，回到实际操作人员或业务 Owner 确认。建议为每类阻断记录原因、影响范围、下一步和责任人。
4. **人确认/接管。** 实际操作人员与业务 Owner 逐步审核；对不可逆动作、敏感数据、跨系统提交和规则不确定项，要求人工确认或直接接管。iCEO 不替代业务决策，也不补造成功决策执行。
5. **受控执行与状态回写。** 经审核的步骤先在沙盒验证正常与异常路径，再按最小权限进入受控执行。每次运行写回状态、输入版本、规则版本、人工修正、失败原因和最终业务结果；失败或修正回流到知识和 SOP。
6. **最终结果。** 结果应能回答“完成了什么、谁确认、哪些步骤由人完成、哪些证据仍缺失”。当前输入没有提供实际执行结果、成功率、自动化比例或业务收益，均为【待补证据】。

##### D1.2.5.3 实施过程、困难与采用机制【建议】

**输入与建设过程。** 建议先选择一个边界清晰、可在沙盒复现的流程样本；收集授权说明、视频或共享样本、角色/系统清单、正常路径和至少一个异常路径。先产出结构化 SOP 草稿，再由实际操作人员逐步核对，最后设计 Agent、Tool 或 Workflow 的最小能力卡。不要把整段流程一次性产品化。

**可能困难。** 输入只说明知识采集容易遗漏页面切换、口头判断、手工步骤和未记录经验，并未证明实际项目已发生具体阻力。建议将可能困难分为：视频质量不足；屏幕或资料含敏感信息；跨系统上下文丢失；例外没有被演示；权限与责任人不清；业务 Owner 没有时间复核；以及沙盒与生产环境不一致。所有项在首次试做时记录为“已发生/未发生/待验证”。

**克服机制。** 建议使用最小可复现样本、时间点引用、步骤级不确定性标签、双人审核、异常路径清单和沙盒回归；对敏感信息实施脱敏、范围限制、临时缓存与原始视频留存决策分离。原始视频是否临时缓存、抽检、回放或长期保留，以及部署于 Edge Server 还是其他环境，需由业务、安全与相关审批方共同确认。

**推动采用。** 让实际操作人员先看到自己的演示如何变成可修改的 SOP 草稿，允许其直接纠正步骤和规则；以一个小范围流程交付能力卡、验收清单和责任人，而不是要求先完成全量治理。可设立短周期复盘：新增例外、人工接管、失败原因和规则变化进入待审队列。是否已有采用者、培训安排、使用频率和持续运营人尚不明确，列为【待补证据】。

##### D1.2.5.4 组织与价值证据【建议】

**职责变化假设。** 业务人员从“写完整 SOP 的单一知识提供者”转为“演示、解释和审核者”；业务 Owner 负责范围、验收和风险取舍；COO AI Team/Hollis 负责与 ITEM 的共同开发衔接和现有成果扩展；DT 按需提供数据、代码、软件、接口及跨部门支持；运营责任人负责版本、例外、回滚和运行记录。以上是建议职责模型，不是已完成组织转型。

**验收建议。** 以同一流程的改造前基线和改造后试运行作对照，至少固定：任务定义、分母、观察周期、样本量、正常/异常路径、人工接管口径、错误等级、敏感数据事件口径、成本口径和维护次数。建议分开记录知识质量（漏项、误解、修正量）、流程质量（完成/阻断/回滚）、运行质量（失败原因、延迟、人工时长）和业务结果；不能用任意一个指标替代全部价值。

**待补实测结果。** 当前输入没有给出任何 KPI、运营结果、组织转型结果、排名或模型能力数据。待业务 Owner 确认：改造前平均采集耗时；漏项与专家修正量；正常/异常样本数；人工接管率；错误严重度；沙盒与受控执行差异；维护周期；成本变化；用户采用率；以及最终业务结果。没有这些数据时，只能写“待测”，不能写达标或提升百分比。

##### D1.2.5.6 思考：变更链与可沉淀资产【建议】

**业务变更链。** 建议固定为：业务提出规则或流程变更 → 实际操作人员/专家审核 → ITEM 与 COO AI Team/Hollis 共同开发，必要时由 DT 支撑 → 使用正常/异常样本回归 → 业务 Owner 验收 → 受控发布 → 监控、人工接管与回滚。任何规则变更必须有版本、提出人、审核人、影响范围和生效/回滚条件。

**可沉淀到核心知识库的授权知识。** 在得到相应授权后，可沉淀结构化 SOP、术语/字段定义、角色与权限、判断规则、异常分类、系统接口约束、审核记录、运行失败原因、人工修正模式、评测样本和运营机制。原始视频是否长期保存不能默认决定；采集、处理和留存必须分开审批。

**第二场景复用。** 可复用：视频/示范采集模板、步骤级证据结构、缺失信息问法、人工接管协议、版本与回滚字段、沙盒回归清单、验收分母与错误等级、运营复盘模板。必须重验证：新场景的授权与敏感数据边界、系统接口、字段语义、业务规则、异常分布、角色权限和最终结果定义。不能因为流程都能录屏就假设 Agent 能力可直接迁移。

##### D1.2.5.7 可重复交付与动手【建议】

**通用交付流程。** 1）筛选可复现且边界清楚的流程；2）确认授权、数据与留存策略；3）录制或导入共享示例；4）提取步骤、条件、输入、切换、人工动作、例外与结果；5）生成带证据和不确定性标注的 SOP；6）由实际操作人员和业务 Owner 审核；7）拆分 Agent、Tool、Workflow 或保留人工步骤；8）在沙盒跑正常/异常路径；9）按权限受控发布；10）记录状态、修正、失败、验收与回滚；11）将新知识回流并回归。

**交付分层。** 核心层包括采集协议、证据结构、审核、权限、回滚、评测与运营；配置层包括角色、字段、业务规则、异常分类、提示/Skill 和交接；接口层包括系统读写、状态回写和日志；维护层包括版本、例外队列、回归、发布和停止条件。每层都要有 Owner，不把不确定项隐藏在一个“自动化完成”标签下。

**会中动手。** 建议现场选一个低风险、可脱敏或模拟的步骤，修改一条业务规则或流程分支；产出小范围 SOP 草稿/能力卡、一个正常样本、一个异常样本、验收项、人工接管条件、责任人和回滚条件。修改前后都保留版本和审核人，便于说明变更链如何工作。

**失败、缩小或停止。** 若视频无法证明关键规则、授权不完整、接口无法安全回写、异常路径不可控或业务 Owner 无法验收，应缩小范围、保留人工步骤、转交相应责任方或停止该场景；不得为了“可重复交付”而强行产品化，也不应把失败原因改写为模型能力问题。

##### D1.2.5.8 既有详细实践与边界补充

##### 验证点：降低知识采集门槛，特别是线下流程

适合业务人员难以清晰描述、但能够直接演示的流程，例如 backlog 处理、物流数据采集、线下资料整理或跨系统操作。“Offline”在这里指线下或尚未被系统完整记录的业务活动，不默认等于所有技术处理均不联网。

##### 痛点

让业务人员先写出完整 SOP、明确每个字段与例外，往往门槛很高。真实工作还包含页面切换、口头判断、手工步骤和未记录的经验，单靠访谈容易遗漏。

##### 解决路径

**视频 → SOP → Agent → 执行。**

1. 在授权范围内录制操作或导入可共享的示例视频，保留必要背景和角色信息。
2. 提取操作顺序、输入、判断条件、系统切换、人工动作、例外和结果。
3. 生成 SOP 草稿，标注不确定步骤、缺失信息和可能的自动化点。
4. 由实际操作人员及业务 Owner 审核，确认哪些步骤能够转成 Agent、Tool 或 Workflow。
5. 在沙盒中验证正常与异常路径，再按权限进入受控执行。
6. 将运行失败、人工修正与结果返回知识和 SOP。

##### 持续优化：全方位录屏与被动知识收集

从业务人员主动提供一段视频，演进为对授权范围内真实操作的持续观察，减少额外填写和回忆负担。被动采集不代表未经告知的监控；采集目的、用户授权、屏幕范围、敏感信息、访问权限和停止条件必须明确。

**采集/处理视频与长期留存原始视频是不同决定。** 旧稿“不存原始视频”可作为默认数据最小化选项：完成提取后保留结构化记录和审核结果。是否允许临时缓存、抽检、回放或保留原视频，以及保留多久、部署于 Edge Server 还是其他环境，由业务、安全与相关审批方共同确认。

##### 演示与证据

展示一段业务人员实际操作如何形成 SOP 草稿，哪些步骤被系统明确标为不确定，以及经审核后能否形成可执行的 Agent。对比知识采集耗时、遗漏、专家修正量和后续维护成本。

**本节结论：**ISS 哪些流程“做得出来、说不清楚”？谁能提供和审核演示？采集、留存与执行权限怎样确定？
