#### D1.2.3 UNIS Rate & Quote｜60 分钟

##### D1.2.3.1 业务结果、改造前流程与预录视频位（建议设计）

**已知业务痛点。**业务人员表达的是报价、费率、客户、运输条件和可执行方案；开发人员面对的是不同系统、表格及字段。双方反复沟通，却可能对同一个字段、规则或计算条件有不同理解。

**期望结果（建议验证，不是已实现结果）。**

- 形成一套由授权数据提出、由业务专家确认的客户、服务、运输、费率、报价及其条件的共享语义。
- 让分析页面和应用表单共用同一本体；业务人员能看到数据口径、条件影响、结果来源和缺失信息。
- 把报价建议与正式对外报价分开授权；异常报价、缺失条件和超出边界的情形交给人。
- 通过一个边界清晰的小范围，验证业务概念理解是否一致、规则来源是否可追溯、分析与表单是否共用语义。

**改造前流程（建议用会中实际流程校准）。**业务提出报价需求 → 通过不同系统、表格或字段寻找数据 → 业务与开发反复解释字段、规则和计算条件 → 得出分析或报价建议 → 对缺失条件、异常报价和正式对外报价进行人工判断。上述链路是基于原案例痛点的工作假设，具体系统名称、交接人、审批节点、耗时和失败点均为待补证据。

**预录视频建议。**录制一条从一份授权真实数据开始的连续演示：对象/关系候选 → 业务审核 → 自定义数据分析页面 → 应用表单 → 一个规则修改如何同步影响分析口径和表单校验 → 异常报价进入人工确认。视频中明确区分：真实数据（须获授权）、脱敏数据（用于保护敏感信息）和模拟数据（仅用于展示路径）。正式对外报价不要在未经确认的演示环境中执行。

**待补证据。**UNIS 当前报价流程图、实际系统/表格清单、业务与开发交接点、授权样本、正式报价审批边界、视频可用素材及脱敏规则。

##### D1.2.3.2 改造后闭环：正常任务、异常与状态回写（建议设计）

**正常任务。**建议以一个范围清楚的 Rate & Quote 子流程开始：输入客户、服务、运输条件、费率、报价条件及必要的有效期；系统基于已审核本体识别对象和关系；分析页面展示口径、条件影响、来源和缺失信息；应用表单执行字段校验并生成报价建议。报价建议不等于正式对外报价。

**缺失信息与异常。**缺失客户、运输条件、有效期或其他必需条件时，页面应标明缺口并停止自动推进；规则冲突、超出有效期、无法解释的计算差异或异常报价进入人工判断。建议保留异常类型、输入版本、规则版本、处理人、决定和理由。

**人确认/接管。**业务专家确认语义、例外和决策边界；经授权人员确认是否接受报价建议；正式对外报价必须经过既定权限与审批。若证据不足，流程应澄清、拒答或转人工，而不是补造成功决策执行。

**状态回写与最终业务结果。**建议将“草稿、待补信息、待专家审核、建议生成、待正式授权、已确认、退回/停止”等状态与来源记录关联，并在实际使用和业务结果出现后反向更新本体与规则。状态名称、回写目标系统、接口、最终业务结果定义和可回放记录格式均为待补证据；本案例没有已实现运营结果可供宣称。

##### D1.2.3.3 实施过程、困难与采用（建议设计）

**输入与建设过程。**

1. 取得授权的真实数据、字段说明、现有报价材料和最小业务范围。
2. 从数据识别对象、字段、关联和状态候选；同时登记数据版本和来源。
3. 与业务专家逐项审核客户、服务、运输、费率、报价、条件、有效期、例外和计算规则。
4. 将已审核定义建成小本体，并围绕同一本体生成自定义数据分析页面、应用表单、字段校验和必要的受控 Action。
5. 用正常、缺失、冲突和异常样本回放，记录预期、实际、人工判断及规则版本。
6. 通过小范围演示和业务验收，再决定补充条件、扩大样本或停止/缩小。

**可能困难（不是已证实历史阻力）。**数据字段缺少业务语义、不同来源口径不一致、例外未被样本覆盖、规则依赖有效期或上下文、页面与表单各自维护定义、权限或接口不清晰，都可能使本体失效或难以验证。

**建议的克服机制。**候选与已确认语义分层；每条规则记录来源、确认人、版本和生效范围；建立异常样本集；分析页面与表单从同一版本生成；每次规则变更做回归；正式报价保留权限门；无法确认时转人工或停止，不强行产品化。

**推动采用与持续改进。**建议先让业务专家参与字段/规则审核，并让一线使用者用真实但受控的样本完成任务；收集概念误解、缺失条件、误报/漏报和接管理由，按周期评审本体与规则。具体采用率、培训完成率、反馈量和运营周期为待补实测数据。

**专家审核机制（建议）。**每个对象、关系、条件、计算规则、例外和正式行动边界都要有业务审核记录；审核不通过时保留原因和回退版本。业务 Owner 与验收人可以兼任，但责任字段不能空缺。

**验收与基线（建议先定义，不能写成 KPI）。**以预先锁定的样本集和业务边界为分母，按一个约定周期回放：概念理解一致性、必填条件完整性、规则/来源可追溯性、计算差异、异常升级正确性、人工接管记录完整性、分析与表单定义一致性。按严重程度区分字段/语义错误、规则/计算错误、权限/流程错误、数据质量错误和结果记录错误。

**待补实测结果。**样本量与来源、基线周期、各类错误数及分母、人工处理时长/成本、规则变更次数、接管率、回滚次数、正式报价通过/退回情况，以及是否产生可复现的业务结果。目前没有证据支持任何百分比、收益、排名或组织转型结论。

##### D1.2.3.6 思考：业务变更链与可沉淀知识（建议设计）

**业务变更链。**业务提出费率、报价条件或例外规则变更 → 领域专家审核业务含义与边界 → ITEM/FDE 修改本体、规则、页面或表单 → 用正常与异常样本回归 → 业务 Owner 验收 → 按权限发布或回滚 → 运营记录使用、接管和结果 → 反馈回本体与规则。每个节点需要版本、责任人、证据和状态；具体工具与系统待补。

**可沉淀到核心知识库的授权内容。**

- 对象、关系、条件、有效期、计算规则、例外和决策边界的审核定义。
- 正常、缺失、冲突、异常样本及其预期处理、人工决定和来源。
- 页面、表单、字段校验、受控 Action、权限和审批流程的版本记录。
- 评测集、错误级别、回归结果、发布/回滚记录和运营复盘。
- 面向业务用户的使用流程、何时确认/拒答/接管的 Skill，以及维护责任。

**第二场景复用与重验证。**可复用的是审核模板、版本/来源记录、异常分类、回归门、责任字段和运营机制；客户/服务/运输/费率对象的具体语义、接口、权限、计算条件、例外与正式报价边界必须在第二场景重验证。不能因为都使用本体，就把 PEI、UKM、BNP 或其他项目当成同一应用。

##### D1.2.3.7 可重复交付与现场动手（建议设计）

**可重复交付的方法流程。**授权数据与边界 → 对象/关系/状态候选 → 业务审核 → 小本体与规则版本 → 分析页面 → 应用表单与校验 → 正常/异常回放 → 人工接管与权限门 → 验收 → 受控发布/回滚 → 运营反馈。

**通用核心、配置、接口、评测、维护。**

- 通用核心：候选提取、审核、版本、溯源、异常分流、人确认和回写机制。
- 场景配置：客户/服务/运输/费率/报价对象、字段、条件、有效期、例外与错误级别。
- 接口与权限：数据源、状态回写目标、审批、正式报价 Action 和安全边界；均需现场确认。
- 评测与维护：样本集、回归规则、错误分级、发布门、回滚、运营周期和 Owner。

**现场动手（建议产出，不宣称已完成）。**由 ISS Biz (team) 提供一条已授权、可脱敏的最小报价样本；现场修改一条业务规则或报价条件，在草稿中同步展示本体定义、分析页面口径、表单校验、异常路径和权限门；产出一张能力卡、一份小范围验收表和责任字段。正式对外报价仍需按实际审批执行。

**失败/停止机制。**若语义无法由专家确认、样本不足以回放、规则冲突无法解释、接口/权限不清或异常无法安全接管，则缩小范围、转交人工、暂停或停止；不得用演示顺畅替代业务验收，不强行产品化。

##### D1.2.3.8 既有详细实践与边界补充

##### 验证点：从数据生成本体，弥合业务与开发的断节

本体不只是数据库结构或字段说明，而是把业务对象、关系、条件、计算规则和行动组织成共同语言。数据可以提出结构线索，但业务含义必须经过领域专家确认。

##### 痛点

业务人员表达的是报价、费率、客户、运输条件和可执行方案；开发人员面对的是不同系统、表格及字段。双方反复沟通，却可能对同一个字段、规则或计算条件有不同理解。

##### 解决路径

**数据 → 本体 → 自定义数据分析页面 → 应用表单。**

1. 从授权的真实数据识别候选对象、字段、关联和状态。
2. 将客户、服务、运输、费率、报价及其条件映射为可审核的业务概念；具体对象以案例实际数据为准。
3. 由业务专家补充数据中看不到的例外、规则、定义和决策边界。
4. 围绕同一本体生成分析页面，使业务人员能看到数据口径、条件影响和结果来源。
5. 将验证过的定义和规则转化为应用表单、字段校验及必要的受控 Action。
6. 页面使用、报价校验和实际业务结果反向更新本体与规则。

##### 演示与证据

从一份实际数据开始，展示对象/关系候选、业务审核、分析页面、表单和反馈的连续链路。特别说明一个规则修改如何同时影响分析口径和业务表单，避免“分析一套定义，执行另一套定义”。

观察业务概念理解是否一致、规则来源是否可追溯、分析与表单是否共用语义，以及异常报价或缺失条件如何交给人。报价建议和正式对外报价应分开授权。

##### 持续优化与 ISS 迁移

以一个边界清晰的小范围先验证，逐步补充条件、异常与样本，再推广至新的流程。PEI、UKM 等可作为后续最佳实践候选，但须分别确认具体业务目标，不把不同项目仅因都使用本体就视为同一应用。

旧稿中的 BNP → 动态表单 → PEI 仍可保留为本体与应用迁移的补充材料；**它与本次 UNIS Rate & Quote 不是未经确认的同一个项目，不再占用独立主议程时间。**

**本节结论：**ISS 哪些数据能够生成值得审核的业务模型？谁能确认业务语义？分析页面如何进入实际应用而不是停留在报表？
