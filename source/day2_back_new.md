##### D2.4.1 自主 IP 与资产权利边界

“自主 IP”首先指 ISS 能够在授权范围内持续拥有、维护和复用的业务能力组合，不等于自建模型，也不等于所有代码都必须由 ISS 自写。可形成长期差异化的候选资产包括经过审核的领域语义、业务规则与流程模型、可复用 Skill/Workflow、独立评测与回归集、反馈数据闭环、产品工程和交付/运营方法；技术 Marketplace 只负责技术能力的登记、发现、复用和治理，不是外部商业渠道。

| 资产类别 | 本轮应记录什么 | 不能默认的结论 |
|---|---|---|
| ITEM/COO 背景资产 | 既有代码、模型、框架、方法、底座、工具、接口、品牌和交付经验；来源、版本、授权、可带入范围与限制 | 不因共同讨论、调用或演示而自动转移所有权或获得永久授权 |
| ISS 业务资产 | ISS 的业务目标、流程、规则、领域语义、运营机制、经授权的反馈与验收方法 | 客户数据、员工数据、业务事实或特定客户材料不自动成为可自由商业化的 IP |
| 联合新增资产 | 共同定义/实现的配置、Skill、Workflow、评测、连接、文档、产品工程与运行改进；贡献、版本、维护和使用范围 | 不默认全部新增代码、模型、数据、文档或收益归 ISS；不得用“联合开发”替代权利约定 |
| 第三方授权 | 模型、开源组件、软件、数据、接口、客户材料、品牌与服务条款；用途、地域、期限、再许可、留存和退出 | 能技术调用不等于可转售、可训练、可转授权或可对外发布 |

**法务与合同确认清单：**每项资产记录来源、贡献方、权利类型、使用场景、客户/地域限制、保密与数据处理要求、再许可/商业化条件、版本与退出安排；由相关业务、合同/法务及必要的安全、采购、架构责任人确认。会议可以形成边界建议和待确认清单，不自动作出所有权承诺。

##### D2.4.2 可重复交付的候选产品

讨论对象是“候选产品/服务包”，不是宣布 ISS 已有或已售产品。候选必须从一个可验证业务问题出发，说明客户/用户、问题、差异化资产和交付责任；不能只给 Agent 名称，也不能用 Marketplace 的技术登记替代客户获取、合同、交付或售后。

| 候选产品包字段 | 会中需要回答的问题 |
|---|---|
| 客户/用户与问题 | 面向哪类客户、业务域或内部用户？解决哪一个可量化或可观察的问题？首个场景与排除项是什么？ |
| 差异化 | 哪些经授权的领域语义、规则、流程、评测、反馈或交付方法能被第二次复用？为什么不只是通用模型或一次性定制？ |
| 通用核心 + 配置 | 哪些是稳定核心（接口、编排、评测、日志、权限边界、运维机制），哪些必须按客户配置（规则、数据映射、工作流、角色、UI、SLA）？ |
| 评测 | 正常/异常/边界样本、专家判定、业务基线、质量/风险/成本/人工介入和第二客户复验如何定义？ |
| 部署与维护 | 数据部署、接口、版本、回滚、告警、升级、培训、支持、退出和责任由谁承担？ |
| 成本与 SLA | 计算/模型/接口/实施/运维/人工成本如何计量？服务级别、响应、可用性、异常和不适用边界如何约定？未知项保持待确认。 |

候选方向可从已讨论的能力组合中提出，例如服务智能、Back Order/Customer Promise、CEC/Genesys、Service Supply Chain Decision 或 WMS/Warehouse Business Tooling；名称、客户、价格、成熟度、产品责任与商业指标均需验证，不虚构已售产品或已完成商业化。

**最小重复交付证据：**同一通用核心在第二个受控场景/沙盒中复用；客户配置、权限、语义和评测差异被记录；结果、成本、人工介入、运维工作量和失败边界可比较；合同/IP/数据使用和正式审批路径清楚。未达到时，候选仍停留在验证/试点方向。

##### D2.4.3 十二月以后启动的条件与任务

“十二月以后启动”指在十二月之后进入商业验证、客户/内部试点、资源投入和下一决策门的工作方向，不是未经审批的正式上市承诺，也不表示十二月前必须完成平台建设。产品化应从近期并行准备，不能被拖到两年后才第一次讨论；但每一步都要以证据、资源、权利和正式批准为前提。

| 启动条件 | 需要完成的任务 | 输出/决策门 |
|---|---|---|
| 问题与客户假设清楚 | 访谈/内部业务验证，确认用户、痛点、范围、排除项和愿意验证的结果 | 候选问题卡；无证据则缩小或换题 |
| 首个场景有基线与验收 | 准备真实/脱敏材料、正常/异常/边界样本、专家口径、人工边界和业务基线 | 最小验证包；确认继续、补证缩小或暂缓 |
| 通用核心与配置可拆分 | 整理接口、Skill/Workflow、配置、评测、部署、日志、回滚、Training 和维护清单 | 候选产品包与第二场景复用计划 |
| IP/数据/合同边界可审 | 完成背景资产、ISS 业务资产、联合新增、第三方许可和客户材料盘点；法务/合同/安全/采购按需审查 | 授权与合同待办清单；未确认不得对外承诺 |
| 责任与资源可承担 | 明确 ISS Biz 业务 Owner、COO AI/ITEM 共建 Owner、交付/FDE、运维、支持和 DT 按需资源 | 资源/Owner/日期记录；缺口进入下一门 |
| 客户验证与试点批准 | 明确试点对象、环境、数据、SLA/支持边界、费用/成本假设、风险与退出条件 | 试点或商业验证批准；不等于正式上市 |

##### D2.5.1 战略四项成果与执行四字段衔接

战略四项成果回答“ISS 要形成什么转型能力”，执行四字段回答“第一轮现在怎样负责任地开始”。二者是上下层闭环，不互相替代：不能用一个 POC 名称代替战略成果，也不能只讲蓝图而不落到 Owner、日期、边界和下一决策门。

| 战略成果 | 必须形成的判断 | 落入执行四字段的方式 |
|---|---|---|
| ① 目标运营蓝图 | 未来两到三年的业务工作方式、人机分工、专家/主管/跨域协作和共用能力 | 先选一个能代表目标工作方式的首个共建场景；在字段①写用户、流程、基线和验收，在字段②/③写角色与能力边界 |
| ② 现状差距及突破主线 | 以证据说明知识、数据、接口、评测、组织或采用机制的差距、影响和优先级 | 在字段③写已有/缺失输入和真实/模拟/人工边界；在字段④写补证、建设、停止或转交任务 |
| ③ 分层实施路线图 | 业务、组织、平台、产品四条泳道的阶段、依赖、资源、验收和下一门 | 用字段②明确联合团队与 Owner；字段④记录本轮实际阶段、交付、日期、投入和下一评审 |
| ④ 自主能力与商业化方案 | 候选资产/产品、客户价值、权利边界、交付维护责任和启动条件 | 字段①写首个验证问题和排除项；字段③写资产/授权/部署/评测边界；字段④写商业验证是否进入、条件与正式审批 |

**执行四字段固定内容：**

1. **首个共建场景与验收指标：**问题、用户、范围、排除项、业务基线、样本、专家判定、人工确认点和验收门槛。

4. **推进方式与下一决策门：**本轮实际承诺阶段、交付物、资源、Owner、日期、上线/回滚条件、继续/调整/停止/转交结果和下一评审。

##### D2.5.2 收敛规则及领导意见记录

收敛不是重新播放案例或重新盘点所有业务域，而是把两日事实、建议、证据、责任和缺口形成可审阅记录。Tom 先读出建议，再由具备相应职责/授权的领导确认“继续、有条件继续、补证缩小、暂缓转交”之一；未确认的内容保持“待会中确认/待正式审批”。

**收敛规则：**

- 事实、建议、目标、待补证和领导意见分栏；没有来源或责任人的断言不作为已知事实。
- 首个场景必须包含问题、用户、范围、排除项、基线和验收，不接受只写 Agent 名称。
- 每个结论都带 Owner、日期、投入、下一评审和正式审批/转交入口；未定项写“会中确认”。
- 自动、辅助、人工确认、拒答、停止和回滚边界要能回到能力输入与执行边界字段。
- 产品化、商业验证和十二月后启动写成条件化方向；不写成已售、已上市、已批准资源或已完成能力。
- 权利、客户数据、模型/软件/接口和第三方许可按合同/法务确认；会议共识不产生自动所有权或生产权限。
